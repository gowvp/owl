## 二、已实施：登录失败递进锁定

实现位置：`internal/web/api/login_guard.go`、`internal/web/api/user.go`。

当前系统只有一个配置账号，因此只保存一份账号级状态，不按请求中的用户名或 IP 建立记录。不存在的用户名、错误密码、缺少请求字段、无效密文和无法解析的凭据，都按失败计算。更换用户名或请求来源不能获得新配额。

| 触发条件 | 停用时长 |
| --- | --- |
| 累计第 5 次失败 | 1 分钟 |
| 解锁后再次失败 | 5 分钟 |
| 下一次解锁后再次失败 | 60 分钟 |
| 下一次解锁后再次失败 | 8 小时 |
| 此后每次解锁后再次失败 | 8 小时 |

首次四次失败返回原有登录错误；第五次仍返回该次登录错误，同时启动一分钟锁定。锁定期间即使输入正确密码也返回 HTTP 429，附带 `Retry-After`。被锁定拦截的请求不新增失败次数、不延长停用时间；到期时可以重新尝试，失败立即进入下一档，成功则清空累计次数和锁定级别。

中间件放在请求绑定和登录处理之前，并用互斥锁串行核验结果，避免多个并发请求在第五次失败前同时通过检查。状态大小固定，操作复杂度为 O(1)，不存在伪造用户名导致记录表无限增长的问题。

这里的停用只影响 `/login` 新登录，不撤销已经签发的 JWT，也不阻止 APISecret 或第三方 AuthURL 鉴权。状态只存在于当前进程，重启会清零，多实例不会共享。攻击者仍可能通过故意失败锁住配置账号，这是账号级锁定策略的可用性取舍。

## 三、已实施：公开密钥接口每分钟五次限流

实现位置：`RegisterUser`、`newLoginKeyWindow`。

现有依赖中，`web.Limit` 是数值边界函数，HTTP 限流中间件实际名为 `web.RateLimiter`。本轮复用该中间件，设置每分钟五次的补充速率与五次突发容量，再增加固定五个时间戳的滚动窗口。原因是令牌桶允许突发并持续补充令牌，单靠令牌桶不能严格保证任意一分钟最多五次。

前五次可以连续获取密钥，超过滚动一分钟配额的请求返回 HTTP 429。配额由所有来源共享，不按 IP 建表；换 IP 也不能扩大服务端放行数量。两个限流器的状态大小均固定，滚动窗口每次检查为 O(1)。

需要澄清内存问题：当前 `Secret` 只保存一对 RSA 密钥并缓存一小时，源码没有显示每次获取公钥都追加一条密钥记录，因此“无限访问必然导致内存无限增长”尚无复现证据。限流可以约束请求处理量，但不能据此声称已经定位并修复某个已证实的内存泄漏。若仍有内存增长，需要另行结合实际请求量和内存剖析定位。

## 四、已实施：空配置拒绝登录

实现位置：`UserAPI.login`。

删除原先将空配置回填成 `admin/admin` 的逻辑。只要 `Server.Username` 或 `Server.Password` 任意一项为空，所有 Web 登录都返回原有用户名或密码错误，不签发令牌，也不写入默认值；失败仍计入账号锁定。

这只修复空配置恢复默认密码及空凭据登录的问题。`internal/conf/default.go` 和 `configs/config.toml` 当前仍设置 `admin/admin`，所以默认凭据漏洞只能标记为部分缓解，不能宣称彻底消除。把配置清空后，只能由管理员修改本地配置恢复 Web 登录，登录接口不会自动补回账号。

## 五、固定 JWT 签名密钥：新样例已修，历史实例待处理

报告指出旧版本配置中存在公开固定签名密钥，攻击者可以不调用登录接口，直接伪造 JWT 访问受保护接口。因此登录失败锁定和公钥限流不能修复这类绕过。

当前样例的 `JwtSecret` 已在既有提交 `c5be5b7` 中清空。`NewHTTPHandler` 在密钥为空时生成随机值，`DefaultConfig` 本身也生成随机密钥。这是已有修改，本轮没有重复修改。

仍需分析的方案：

1. 历史配置中仍使用公开旧密钥的实例必须轮换；仅更新仓库样例不会改掉已有配置。
2. 如需代码自动处理旧实例，可在启动时识别已公开的旧值，生成新的随机密钥；必须明确持久化行为，并验证旧令牌随之失效。
3. 自定义且未泄露的密钥不应被无条件替换。文档明确密钥的保管、轮换与会话失效规则。

报告对旧版本的影响范围主要是加载仓库原配置的实例；其报告中 Docker 和独立发布二进制会生成新配置，不能把旧固定密钥问题直接归为所有安装方式都受影响。本轮未对历史实例进行轮换，也没有运行报告中的伪造令牌脚本。

## 六、未授权实施的问题及具体方案

### 6.1 默认凭据与首次初始化

报告已用 `admin/admin` 获得管理员令牌。RSA 公钥是公开的，RSA 加密不能阻止知道默认密码的人登录；限流也不能阻止第一次就输入正确默认密码的人。

建议优先设计一次性的本地初始化流程：未设置账号密码时拒绝 Web 登录，由管理员完成初始配置。备选是每实例生成随机初始密码，并通过受控的本地渠道交付。需要先决定用户如何取得凭据及初始化体验，不能直接把默认密码清空却不给新安装用户可用入口。

如果保留临时初始密码，应持久化初始化状态，后端在修改初始密码之前只允许必要的凭据设置接口；前端提示不能代替后端权限控制。还需处理已有默认凭据实例的升级路径。

第二阶段已经实现用户指定的前端修改流程：登录成功后，当用户名和密码都是 `admin` 时返回 `reset_account:true`，其他成功登录返回 `false`。前端保存会话标记，先跳转 desktop，再显示独立弹窗，只有“用户名、密码、再次输入密码”三个输入框。校验空值、两次密码一致以及不保留 `admin/admin`，调用已有 `PUT /users` 加密请求，旧密码固定为 `admin`。保存成功后清除旧会话并重新登录；失败保留弹窗和输入。弹窗不能通过关闭按钮、遮罩或 Escape 跳过，桌面刷新仍显示，且暂停首次桌面引导，避免两个浮层冲突。

本阶段按要求只做响应标记和前端流程，没有增加服务端初始化权限门禁；直接调用后端 API 的客户端仍不受弹窗限制。默认密码生成和历史账号升级方案也没有改变，因此默认凭据漏洞仍未完整消除。

### 6.2 明文密码配置：保留的设计取舍

报告将密码以明文保存在 `config.toml`、登录时直接比较的行为列为 CWE-256，并建议改为密码哈希。项目明确选择保留现有方式：部署主要面向私有环境和家庭，允许管理员直接维护本地账号密码配置，避免增加哈希迁移、凭据拆分和维护复杂度。本项不实施密码哈希改造，也不将明文存储标为已经修复；它是本次确认接受的设计取舍。

这项决定针对本地配置存储，不等于允许保留已知的默认密码。能读取配置文件的人仍能取得密码，这是保留该设计的边界。现有 ONVIF PasswordDigest 校验使用独立 `ONVIF.Password` 的原始密码计算摘要，已不再依赖 Web 的 `Server.Password`。

另一个独立事项是 `internal/web/api/user.go` 的 `updateCredentials`：当前密码为空时，校验旧密码仍回退为 `admin`。它属于密码修改接口的空值行为，与是否明文存储不是同一问题。本轮不改代码，保留为待分析事项。

### 6.3 ONVIF：独立配置凭据，认证与 Web 锁定相互独立

**原问题。** 原实现将 `Server.Username` 和 `Server.Password` 同时用于 Web 登录和 ONVIF WS-Security 认证。未修改默认配置的实例，两者都使用已知的 `admin/admin`；网页修改密码后，ONVIF 对象仍保留启动时的旧凭据。报告提供的 PoC 验证了 Web 登录及配置接口，没有提供 ONVIF SOAP 请求的实测结果。

**已实施的解耦。** 对外提供的 ONVIF 服务现在只使用顶层 `[ONVIF]` 配置，不读取 `Server.Username` 或 `Server.Password`。这组凭据用于 HA、NVR 等客户端连接本系统，不用于本系统连接外部摄像头。配置示例：

```toml
[ONVIF]
  Username = ''
  Password = ''
```

管理员可以填写自定义账号和密码。配置段、字段未定义或值为空时，启动会逐项补全：用户名填 `admin`，密码使用密码学随机源生成 10 位纯数字字符串（允许前导零）。只缺一项时只补这一项，已有自定义值保持不变。新安装配置也使用同一生成规则。自动生成的凭据保存到 `config.toml`，管理员从该文件获取密码；不在日志中输出密码。保存失败则终止启动，避免使用无法恢复的随机凭据；后续重启读取已保存的值，不重新生成。

**修改与升级。** 网页修改账号密码不再影响 ONVIF，ONVIF 配置也不改变 Web 登录。修改 `[ONVIF]` 后需要重启服务生效。旧配置没有该段时，升级后的首次启动会自动生成并保存独立凭据；原来使用 Web 账号密码连接的 ONVIF 客户端需要改用这组新凭据。Web 配置为空时也不会关闭 ONVIF 认证，ONVIF 的空值会在启动时自动补全。

**仍未实施的防护。** `POST /login` 的 `loginGuard` 仍只保护 Web 登录；ONVIF 的两个 SOAP 端点仍由依赖的 `verifyWSSE` 校验 PasswordText 或 PasswordDigest，失败返回 HTTP 401，没有接入 Web 的失败计数与递进锁定。两者现在不共用凭据。ONVIF 独立失败限流或锁定不在本次改动范围内。

**验证范围。** 配置测试覆盖新安装、旧配置缺段、两项为空、单项缺失、自定义值保留、文件持久化与重新加载、保存失败返回错误；隔离 SOAP 请求验证两个端点拒绝 Web 凭据、接受独立 ONVIF 凭据，网页修改后 ONVIF 认证保持稳定。未做真实 HA/NVR 客户端联调，未部署。

### 6.4 ZLM 回调来源校验

报告把它列为附带观察：`/webhook/*` 中部分处理器会更新状态或执行录制操作。修复前 ZLM 回调路由没有统一认证；但 `/webhook/events` 自身已有密钥校验，不应把整个回调组一概写成没有认证。

第三阶段按用户要求已经实现：`NewNodeManager` 在启动时调用 `orm.GenerateRandomString(6)` 生成六位字母数字随机值，只保存在当前进程中；同一次运行内所有媒体节点及重连共用该值，下次启动重新生成。设置媒体回调时，最终 URL 为 `/webhook/on_play?owl_secret=xxxxxx` 这类格式，查询参数始终放在完整路径之后。

ZLM 的八条已启用回调 URL 同步携带该值；LAL 与 ZLM 共用接收路由，因此 LAL 的三条已配置回调 URL 也同步携带。接收端九条媒体回调路由统一校验参数：缺失、空值、错误值、长度不符或重复参数均返回 HTTP 401，不进入业务处理。仅在请求体或 header 中携带值也不会放行。`/webhook/events` 保持原有 AISecret/RecvSecret 校验，不要求 `owl_secret`。

中间件在读取参数后从请求日志使用的 URL 与 RequestURI 中移除 `owl_secret`，避免当前随机值进入应用请求日志。没有增加配置字段、持久化密钥、IP 白名单、签名或重放防护。重启后旧回调地址中的值会失效，自动配置下发会使用新值；手工维护的回调配置也必须同步更新。该值不是 ZLM 自身 API 的 `secret`，也不是事件推送的 `RecvSecret`。
