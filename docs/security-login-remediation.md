## 二、已实施：登录失败递进锁定

实现位置：`internal/web/api/login_guard.go`、`internal/web/api/user.go`。

当前系统只有一个配置账号，因此只保存一份账号级状态，不按请求中的用户名或 IP 建立记录。不存在的用户名、错误密码、缺少请求字段、无效密文和无法解析的凭据，都按失败计算。更换用户名或请求来源不能获得新配额。

| 触发条件 | 停用时长 |
| --- | --- |
| 累计第 5 次失败 | 1 分钟 |
| 解锁后再次失败 | 5 分钟 |
| 下一次解锁后再次失败 | 60 分钟 |
| 下一次解锁后再次失败 | 8 小时 |
| 此后每次解锁后再次失败 | 8 小时 |

首次四次失败返回原有登录错误；第五次仍返回该次登录错误，同时启动一分钟锁定。锁定期间即使输入正确密码也返回 HTTP 429，附带 `Retry-After`。被锁定拦截的请求不新增失败次数、不延长停用时间；到期时可以重新尝试，失败立即进入下一档，成功则清空累计次数和锁定级别。

中间件放在请求绑定和登录处理之前，并用互斥锁串行核验结果，避免多个并发请求在第五次失败前同时通过检查。状态大小固定，操作复杂度为 O(1)，不存在伪造用户名导致记录表无限增长的问题。

这里的停用只影响 `/login` 新登录，不撤销已经签发的 JWT，也不阻止 APISecret 或第三方 AuthURL 鉴权。状态只存在于当前进程，重启会清零，多实例不会共享。攻击者仍可能通过故意失败锁住配置账号，这是账号级锁定策略的可用性取舍。

## 三、已实施：公开密钥接口每分钟五次限流

实现位置：`RegisterUser`、`newLoginKeyWindow`。

现有依赖中，`web.Limit` 是数值边界函数，HTTP 限流中间件实际名为 `web.RateLimiter`。本轮复用该中间件，设置每分钟五次的补充速率与五次突发容量，再增加固定五个时间戳的滚动窗口。原因是令牌桶允许突发并持续补充令牌，单靠令牌桶不能严格保证任意一分钟最多五次。

前五次可以连续获取密钥，超过滚动一分钟配额的请求返回 HTTP 429。配额由所有来源共享，不按 IP 建表；换 IP 也不能扩大服务端放行数量。两个限流器的状态大小均固定，滚动窗口每次检查为 O(1)。

需要澄清内存问题：当前 `Secret` 只保存一对 RSA 密钥并缓存一小时，源码没有显示每次获取公钥都追加一条密钥记录，因此“无限访问必然导致内存无限增长”尚无复现证据。限流可以约束请求处理量，但不能据此声称已经定位并修复某个已证实的内存泄漏。若仍有内存增长，需要另行结合实际请求量和内存剖析定位。

## 四、已实施：空配置拒绝登录

实现位置：`UserAPI.login`。

删除原先将空配置回填成 `admin/admin` 的逻辑。只要 `Server.Username` 或 `Server.Password` 任意一项为空，所有 Web 登录都返回原有用户名或密码错误，不签发令牌，也不写入默认值；失败仍计入账号锁定。

这只修复空配置恢复默认密码及空凭据登录的问题。`internal/conf/default.go` 和 `configs/config.toml` 当前仍设置 `admin/admin`，所以默认凭据漏洞只能标记为部分缓解，不能宣称彻底消除。把配置清空后，只能由管理员修改本地配置恢复 Web 登录，登录接口不会自动补回账号。

## 五、固定 JWT 签名密钥：新样例已修，历史实例待处理

报告指出旧版本配置中存在公开固定签名密钥，攻击者可以不调用登录接口，直接伪造 JWT 访问受保护接口。因此登录失败锁定和公钥限流不能修复这类绕过。

当前样例的 `JwtSecret` 已在既有提交 `c5be5b7` 中清空。`NewHTTPHandler` 在密钥为空时生成随机值，`DefaultConfig` 本身也生成随机密钥。这是已有修改，本轮没有重复修改。

仍需分析的方案：

1. 历史配置中仍使用公开旧密钥的实例必须轮换；仅更新仓库样例不会改掉已有配置。
2. 如需代码自动处理旧实例，可在启动时识别已公开的旧值，生成新的随机密钥；必须明确持久化行为，并验证旧令牌随之失效。
3. 自定义且未泄露的密钥不应被无条件替换。文档明确密钥的保管、轮换与会话失效规则。

报告对旧版本的影响范围主要是加载仓库原配置的实例；其报告中 Docker 和独立发布二进制会生成新配置，不能把旧固定密钥问题直接归为所有安装方式都受影响。本轮未对历史实例进行轮换，也没有运行报告中的伪造令牌脚本。

## 六、未授权实施的问题及具体方案

### 6.1 默认凭据与首次初始化

报告已用 `admin/admin` 获得管理员令牌。RSA 公钥是公开的，RSA 加密不能阻止知道默认密码的人登录；限流也不能阻止第一次就输入正确默认密码的人。

建议优先设计一次性的本地初始化流程：未设置账号密码时拒绝 Web 登录，由管理员完成初始配置。备选是每实例生成随机初始密码，并通过受控的本地渠道交付。需要先决定用户如何取得凭据及初始化体验，不能直接把默认密码清空却不给新安装用户可用入口。

如果保留临时初始密码，应持久化初始化状态，后端在修改初始密码之前只允许必要的凭据设置接口；前端提示不能代替后端权限控制。还需处理已有默认凭据实例的升级路径。

第二阶段已经实现用户指定的前端修改流程：登录成功后，当用户名和密码都是 `admin` 时返回 `reset_account:true`，其他成功登录返回 `false`。前端保存会话标记，先跳转 desktop，再显示独立弹窗，只有“用户名、密码、再次输入密码”三个输入框。校验空值、两次密码一致以及不保留 `admin/admin`，调用已有 `PUT /users` 加密请求，旧密码固定为 `admin`。保存成功后清除旧会话并重新登录；失败保留弹窗和输入。弹窗不能通过关闭按钮、遮罩或 Escape 跳过，桌面刷新仍显示，且暂停首次桌面引导，避免两个浮层冲突。

本阶段按要求只做响应标记和前端流程，没有增加服务端初始化权限门禁；直接调用后端 API 的客户端仍不受弹窗限制。默认密码生成和历史账号升级方案也没有改变，因此默认凭据漏洞仍未完整消除。

### 6.2 明文密码存储及密码修改兜底

`user.go` 当前直接比较配置中的明文密码；`updateCredentials` 在当前密码为空时仍回退到默认密码。这一独立路径本轮没有修改，后续应去除兜底并统一凭据状态语义。

Web 登录可采用带盐密码哈希及匹配验证，同时设计旧配置迁移与密码更新的写入规则。但 ONVIF PasswordDigest 计算依赖原始密码，不能简单把共享 `Server.Password` 替换成哈希，否则现有 ONVIF 认证会失效。需要先决定是否拆分 Web 和 ONVIF 凭据，或采取其他可兼容的存储方案。

### 6.3 ONVIF 默认凭据及空配置行为

`internal/web/onvifserver/register.go` 把同一配置账号密码传给 ONVIF 服务，本轮 `/login` 锁定中间件不会覆盖 SOAP 端点。

此外，当前 ONVIF 依赖的 `server.Config.AuthEnabled` 在用户名、密码都为空时关闭认证。因而“清空配置可拒绝 Web 登录”不等于“整个系统停用认证”；这是本轮核对共享凭据时发现的额外行为，需要单独决定 ONVIF 空配置应拒绝请求还是禁用服务。

方案是先同步定义默认凭据和空配置语义，再增加 ONVIF 认证失败计数、来源限流，验证标准客户端仍可正常连接。不可只调整 Web 登录后就宣布 ONVIF 问题已修复。

### 6.4 ZLM 回调来源校验

报告把它列为附带观察：`/webhook/*` 中部分处理器会更新状态或执行录制操作。当前 `setupRouter` 注册 ZLM 回调时没有传入统一认证中间件；但 `/webhook/events` 自身已有密钥校验，不应把整个回调组一概写成没有认证。

建议为其余 ZLM 回调添加专用随机密钥校验，并同步 ZLM 回调配置，先验证合法回调能通过、伪造请求被拒绝且没有业务副作用。必要时补充可信来源约束；如设计签名，还应定义时间戳与重放防护。该方案涉及媒体服务联动，本轮只记录，不修改回调协议。
